# PHASE CLEANUP-27 — test-suite audit, test by test

**Question:** with the gate proving the canonical run byte-identical, is the
test suite still needed?

228 collected tests / 180 test functions / 19 files, inventoried individually
(`gate/_run/test_inventory.tsv`, generated by `gate/_run/test_inventory.py`).

**Answer: yes — but a quarter of it should go.** The reasoning below is the
point; the recommendation falls out of it.

---

## 1. First, what the gate can and cannot prove

The gate replays **one config** and compares 2 077 rows × 132 928 fields to a
frozen baseline. On that config it is close to unbeatable: it caught an injected
1e-10 change at row 11.

What it structurally **cannot** do:

| | why |
|---|---|
| prove a physics identity | it proves *reproducibility*, not *correctness*. A wrong-but-stable change passes. |
| exercise another config | `r_com` at 3 m, tight rate bounds, `torso_mass=0`, inverted `hw` bounds — the canonical visits none of these |
| exercise a non-canonical branch | 5 of 6 AOCS laws, `_solve_strict`, 6 `ik` functions, all of `diagnostics/` |
| check error handling | NaN input, wrong-size `x0`, infeasible solve, stale warm start |

Those four gaps are exactly where the suite earns its place — or fails to.

### Two findings the coverage diff produced on its own

**`wholebody_qp.py`: suite-only = 0.** The 8 failing `test_reworked_qp` tests add
**zero reach** — every line they touch, the canonical already executes (256
gate-only lines). Their value is therefore purely as *correctness assertions* on
already-exercised code, not as coverage. That is a legitimate kind of value, but
it is a weaker case than "they test what nothing else does", and it should be
argued on its merits rather than on coverage.

**`_solve_strict` is covered by nothing, and `CARRYOVER` §B2 is wrong about why
it is kept.** §B2 justifies keeping it as having *"2 test users + 6 script
users"*. Measured:

```

grep for _solve_strict | 'strict' across the WHOLE repo, Misc included:
  -> one hit, the docstring of WholeBodyQPConfig.method
```

**Zero consumers anywhere.** 76 statements, the largest single block verified by
nothing, kept on a justification that does not hold. Fifth instance in this
chantier of an inherited claim failing on measurement — and this one was found by
a tool built for a different purpose, which is the argument for having the tools.

## 4. The `test_reworked_qp.py` question

All 8 fail, and they are the only component-level tests of the **canonical
controller itself** (`WholeBodyQP`). That combination is uncomfortable: the most
important module has the least trustworthy tests.

Three possibilities per test, and they need separating before any action:

1. **thresholds predate the 2.5 freeze** — the test is right in spirit, its
   numbers are stale. Fix the numbers.
2. **the feature under test is off** — `TestT8SoftCoMEffect` with
   `alpha_com_soft = 0.0`. Retire.
3. **a real defect** — the QP does not do what the test says. Would be serious.

Nothing in this audit distinguishes (1) from (3), and guessing is exactly what
this chantier has been correcting. **That is the next piece of work**, and it is
worth doing precisely because these 8 sit on the canonical controller.

---

## 5. Recommendation

**Keep the suite.** It covers what the gate structurally cannot: physics
identities, off-canonical configs, non-canonical branches, and error handling.
Deleting it would leave the repository with excellent *reproducibility* and no
*correctness* checking at all — and the chantier has already shown that a
confident wrong claim survives indefinitely when nothing measures it.

Concretely:

| action | tests |
|---|---:|
| **keep as-is** (A + B + C) | **154** |
| **retire** — `test_mid_waypoint_reshape` ×3, `test_reworked_qp` ×8 | 11 |
| **move** — `test_torso_planner_piecewise_continuous` → `test_planners_6d.py` | 1 |
| **diagnose then decide** — the 8 `test_reworked_qp` (§4) + `test_far_infeasible` | 9 |
| **fate follows their subject** — `test_diagnostics` (10), `test_trajectory_aware_ik` (4) | 14 |

**And gate it.** Once the retirees are gone and §4 is diagnosed, the suite should
be green and then *enforced* — otherwise it drifts again, exactly as it drifted
from a documented "2 failures" to a measured 12 without anyone noticing. A suite
nobody runs is not a safety net; it is a claim about a safety net.

Suggested split, since a 10-minute suite will not be run per-commit:
- **per-commit**: classes A + C (identities and robustness) — fast, no IPOPT
- **pre-merge**: the whole suite plus the gate
